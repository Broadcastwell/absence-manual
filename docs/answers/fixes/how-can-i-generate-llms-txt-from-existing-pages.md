# How can I generate llms.txt from existing pages?

A reviewed page inventory gives an llms.txt generator its titles, URLs and approved descriptions. Study 7 extracted 2,003 criteria from 2,093 eligible answers captured on 22 and 23 September 2026, retaining 10,547 supporting spans. That is a traceability example, not a test showing that an automatically generated file changes AI visibility.

## What we measured

**Measured.** [Study 7's method](https://doi.org/10.5281/zenodo.23271935) extracted AI-stated criteria before the first vendor name across 14 software categories. The published record connects those criteria to supporting spans and dated page comparisons. They are not independently validated buyer requirements or tested product capabilities, and team review remains in progress. Its derived 2,093-answer base is separate from the Index's 2,095 valid answers.

**Reported.** The [current llms.txt proposal](https://llmstxt.org/), read 28 October 2026, describes a concise Markdown guide with links to fuller material. Generation can therefore organise approved records without inventing new descriptions.

## What this means for you

**Reasoned.** Give the generator a source table containing the canonical URL, approved title, short description and any date or scope needed to understand it. Keep an entry's provenance in your internal record. If the description has not been approved, leave it for editorial review rather than deriving a product promise from a heading.

Use one authoritative inventory for additions, changes and removals. Decide which page types belong in each group and give records a consistent order. A repeat generation from the same inputs should produce the same meaningful content, making an unexpected change easy to inspect.

Review the difference before publishing. A moved page needs a current destination; a historical page may need an archive label. Preserve unrelated approved entries when adding new answers. A generator should not replace client descriptions, research limitations or live commercial wording simply because a new section is being added.

Then check the served file, not just the local output. Open a few destinations from each changed group and confirm that their public text supports the generated descriptions. Save the input version, output version and delivery check together. That record demonstrates what was generated and served; later AI use needs different evidence.

- **For a developer:** make the source inventory and selection rules inspectable.
- **For an editor:** approve changed descriptions before they enter the output.
- **For a publisher:** preserve a delivery receipt for the generated version.
